# GitHub Actions live socket

## Summary

The `wss://alive.github.com` connection is created by GitHub's own live-update
code. The hostname and signed socket URL originate in the server-rendered HTML
for the GitHub Actions job page. A GitHub JavaScript bundle reads that
configuration, creates a SharedWorker, and passes the URL to it. The
SharedWorker then opens and maintains the WebSocket.

This was established from two Chrome HAR captures:

- `gha-page-log.har`: the `github.com` page target
- `gha-worker-log.har`: the SharedWorker target

The socket appears only in the worker capture because a SharedWorker has its
own DevTools/network target. It is not evidence that the connection was
created independently of the page.

## Captured page

The relevant document response was:

```text
GET https://github.com/recallai/nebula/actions/runs/30412188809/job/90452056448?pr=11593
Started: 2026-07-29T01:01:24.935Z
Status: 200
Resource type: document
```

Its HTML `<head>` contained both the socket configuration and the worker
source:

```html
<link
  rel="shared-web-socket"
  href="wss://alive.github.com/_sockets/u/<user-id>/ws?session=<signed-session>"
  data-refresh-url="/_alive"
  data-session-id="<shared-worker-session-id>"
>
<link
  rel="shared-web-socket-src"
  href="/assets-cdn/worker/socket-worker-89f8a0e9fe180a48.js"
>
```

The document's Content Security Policy also explicitly allowed:

```text
connect-src ... wss://alive.github.com wss://alive-staging.github.com ...
worker-src github.githubassets.com github.com/assets-cdn/worker/ ...
```

Therefore, `alive.github.com` was a literal value supplied by GitHub's HTML
response. It was not discovered through DNS redirection, generated by the
extension, or injected by a third-party script.

## Page-side worker creation

A GitHub asset recorded in the page HAR,
`https://github.githubassets.com/assets/56089-2b0c6f7c187384e0.js`,
contains the page-side socket setup.

In readable pseudocode, the setup does the following:

```js
const workerSource =
  document.head.querySelector('link[rel=shared-web-socket-src]').href

const socketLink =
  document.head.querySelector('link[rel=shared-web-socket]')

const socketUrl = socketLink.href
const refreshUrl = socketLink.dataset.refreshUrl
const sessionId = socketLink.dataset.sessionId

const worker = new SharedWorker(`${workerSource}?module=true`, {
  name: `github-socket-worker-v3-${sessionId}`,
  type: 'module',
})

worker.port.postMessage({
  connect: {
    url: socketUrl,
    refreshUrl,
    options: {},
  },
})
```

GitHub falls back to a page-local socket implementation when SharedWorker is
unavailable or when `localStorage.bypassSharedWorker` is set to `"true"`.

## Worker-side WebSocket

The worker HAR contains one WebSocket request:

```text
GET wss://alive.github.com/_sockets/u/<user-id>/ws
    ?session=<signed-session>
    &shared=true
    &p=<connection-id>

Started: 2026-07-29T01:02:51.695Z
Origin: https://github.com
Resource type: websocket
Status: 101 Switching Protocols
```

The signed `session` value in this request exactly matches the value supplied
by the Actions page HTML. The worker added the `shared=true` and `p=...`
parameters when establishing the connection.

The WebSocket request's initiator stack points entirely at:

```text
https://github.githubassets.com/assets/socket-worker-89f8a0e9fe180a48.js
```

The stack ends under a `setTimeout` scheduled by `socket.onclose`, so the
specific connection present in the worker HAR was a reconnect rather than the
worker's first connection attempt.

The upgrade response identifies the endpoint as GitHub's Alive service:

```text
HTTP 101 Switching Protocols
Server: github.com
x-github-alive: GitHub Alive (...) @ frontend-...
```

## Connection sequence

```text
GitHub Actions document response
  |
  |  <link rel="shared-web-socket" href="wss://alive.github.com/...">
  |  <link rel="shared-web-socket-src" href="/assets-cdn/worker/socket-worker-...js">
  v
GitHub page JavaScript
  |
  |  new SharedWorker(...)
  |  port.postMessage({connect: {url, refreshUrl, ...}})
  v
GitHub socket SharedWorker
  |
  |  new WebSocket(pageSuppliedUrl + workerParameters)
  v
wss://alive.github.com
```

## What the socket carried

After connecting, the worker sent a subscription message for several signed
GitHub channels. Decoding the signed channel payloads showed channel names
including:

```text
notification-changed:<user-id>
check_suites:82434231333
check_runs:90452056448
actions_results:<opaque-result-id>
repo:<repository-id>:user:<user-id>:settings
```

The server acknowledged the subscription and then delivered live messages
such as:

```text
check_suite #82434231333 updated: in_progress
```

This confirms the practical purpose of the connection: GitHub uses Alive to
push live state changes for the Actions job page and other GitHub UI state.

## Implications for GHA++

- A page-target network observer may not see the socket because its owner is a
  separate SharedWorker target.
- The SharedWorker can survive GitHub soft navigations and can be shared by
  multiple same-origin tabs. Its lifetime does not necessarily match one
  Actions document.
- The stable integration points visible to the page are the two `<link>`
  elements and GitHub's DOM/event behavior. The signed socket and channel
  formats are internal, ephemeral implementation details.
- Connecting directly to Alive would require GitHub-issued signed session and
  channel tokens. GHA++ should not persist or publish those values.
- The page supplies `/_alive` as the endpoint for refreshing an expired socket
  URL.

## Security note

HAR exports contain authentication-adjacent data, including signed socket
sessions, signed channel subscriptions, user and repository identifiers, and
normal authenticated request headers. Even if the socket tokens are
short-lived, the original HAR files should be treated as sensitive and should
not be committed to the repository or shared publicly without sanitization.
